If you are a developer building an enterprise agent, Ampersand enables your agent to reliably work across your customers’ systems of record. More specifically, you can:

- Read historical and current data from your customer’s SaaS.
- Write data to your customer’s SaaS.
- Subscribe to events (creates, deletes, and field changes) in your customer’s SaaS.

Ampersand’s declarative interface and UI components let your customers configure integrations for their instance of Salesforce, NetSuite, and other supported systems, directly inside your product.

[Quickstart →](/starter-project) · [Explore supported systems →](/provider-guides/overview)

## Built for each of your customers’ configurations

**Ampersand handles multi-tenancy at scale.** Say you have 400 customers on Salesforce. Every one of them has customized it to reflect how they run their business, with different custom objects, fields, permissions, and rules for how your product interacts with their data. Two very similar companies can store the same data in completely different places.

Ampersand separates the integration you build from each customer’s configuration. You define the schema and operations your application needs once, and each customer’s installation maps them to their own instance. For example, you define `renewalDate` once, and each customer maps it to wherever their Salesforce keeps it:

| Customer | Where `renewalDate` lives |
|---|---|
| Customer A | `Account.Renewal_Date__c` |
| Customer B | `Account.Contract_End__c` |
| Customer C | `Subscription__c.End_Date__c` |
| …397 more | Each set by the customer during setup |

Your application reads and writes `renewalDate`. Ampersand translates it to each customer’s field.

## How Ampersand works

<Steps>
  <Step title="Define an integration">
    Use an `amp.yaml` file to declare each integration: the system to connect to, the objects and fields to read or write, and the configuration options to expose to your customers. See the [manifest reference](/manifest-reference).
  </Step>
  <Step title="Let customers connect and configure">
    Embed authentication and configuration in your product with the [prebuilt UI components](/embeddable-ui-components), the [headless UI library](/headless), or the [API](/api/overview). Customers connect their own instance and choose field mappings and preferences, and Ampersand saves those choices in their installation.
  </Step>
  <Step title="Ampersand runs it">
    A managed runtime tracks every customer’s configuration and makes the right API calls for each one. It handles authentication, scheduling, retries, and cost, and parses provider error messages. Results are delivered to your [destinations](/destinations/overview).
  </Step>
  <Step title="Monitor, adapt, and recover">
    Inspect installations and operation logs, get [notifications](/notifications/overview) about connection issues, sync failures, and configuration changes, and [watch for schema changes](/manage-customer-schemas#watch-schema-changes) when fields are added, removed, or modified. Use these signals to build self-healing loops in your product: diagnose an issue, refresh metadata or update configuration, and retry once the cause is resolved.
  </Step>
</Steps>

## Guides

The hard parts, already handled.

### Reads and backfills

- [Backfill historical data on install](/read-actions#backfill-behavior): none, full history, or time-boxed per object, with an API to monitor progress.
- [Read only the records that match](/read-actions#filter-by-field-values): per-installation field filters, plus backfill-specific filters for the initial sync.

### Writes that respect customer data

- [Bulk writes with retries built in](/write-actions#write-modes): batching, async mode, and exponential backoff for up to 48 hours.
- [Never clobber customer data](/write-actions#prevent-overwriting-of-customer-data): control per field whether Ampersand writes on create, on update, or only when the field is empty.

### Real-time events

- [Watch individual fields, not whole objects](/subscribe-actions#specify-fields-to-watch): subscribe to updates only for the fields you list, quota-optimized at the source.
- [Track when records are linked, not just changed](/subscribe-actions#association-changes): subscribe to association changes.
- [Get notified when integrations change](/notifications/overview): events for installs, config changes, completed backfills, and paused syncs.

### Schemas and mapping

- [Map nested and dynamic fields](/object-and-field-mapping#user-defined-mapping): nested JSON paths, value mapping, and per-customer field sets.
- [React when a customer's schema drifts](/manage-customer-schemas#watch-schema-changes): get events when fields are created, deleted, or change type.
- [Create custom fields in the customer's SaaS](/manage-customer-schemas#create-or-update-custom-fields): upsert custom fields programmatically.
- [Support multiple CRMs with one manifest](/unified-api): shared object names, per-provider overrides, no forked code.

### Running in production

- [Verify every webhook cryptographically](/destinations/webhooks#webhook-signature-verification): Svix-signed payloads, plus payload size and frequency controls.
- [Stay under provider rate limits](/proxy-actions#use-ampersand-to-manage-api-rate-limits): throttle mode returns a retry-after instead of burning 429s.
- [Call the API from the browser, safely](/api/jwt-auth): short-lived JWTs signed by your server, no API keys in frontend code.
